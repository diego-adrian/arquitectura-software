DDD

Domain-Driven Design · diseño orientado al dominio
EnfoqueEric Evans · 2003

Diseñar el software alrededor del negocio: hablar su idioma, separar las partes donde las palabras cambian de significado y poner las reglas importantes en objetos que las protejan.

EEstratégicoLenguaje ubicuo, contextos delimitados y cómo se relacionan. Decide las fronteras.
TTácticoEntidades, objetos de valor, agregados, eventos. Da forma al interior de un contexto.
Origen
Eric Evans publica Domain-Driven Design (2003), el «libro azul». Vaughn Vernon lo condensa en DDD Distilled (2016).
Qué resuelve
Que el negocio y el código digan lo mismo. Que las reglas vivan en un solo lugar y no se traduzcan en cada conversación.
Cuándo
Dominios con reglas ricas que cambian: reglamentos, seguros, logística, banca. Ahí el modelo es la ventaja.
Cuidado
En un CRUD simple es ceremonia. Y usar entidades y agregados sin lenguaje ni fronteras es copiar la forma sin el fondo.
En CupoEl programa pide DDD estratégico: lenguaje y fronteras. Lo táctico lo usamos lo justo para que el reglamento tenga un lugar donde vivir.
Estratégico primero: sin fronteras, lo táctico no tiene dónde apoyarse.iSAQB · SEI6 / 18

Contexto delimitado

Bounded context · una frontera donde cada palabra tiene un solo significado
Estratégico
«Un contexto delimitado es una frontera semántica: dentro de ella, cada término del lenguaje ubicuo tiene un significado específico.»
Vaughn Vernon · Domain-Driven Design Distilled, cap. 2 (traducción libre)

Cada contexto tiene su propio modelo y su propio lenguaje. No se busca un modelo único para toda la empresa: se busca que cada uno sea coherente por dentro.

Entidad e invariante

Paralelo: el único que conoce la regla del cupo
Táctico
EntidadIdentidad que dura en el tiempoDos paralelos con el mismo cupo y horario siguen siendo distintos: los distingue su id, SIS-211-B.
InvarianteUna regla que siempre se cumple«Nunca más inscritos que el cupo». Si vive en un objeto, no se puede saltar.

Antes

La regla se calculaba en 3 archivos: inscripciones, oferta y reportes, cada uno a su manera.

src/inscripciones/dominio/paralelo.ts 
// El ÚNICO lugar que conoce la regla
// "nunca más inscritos que el cupo".
export class Paralelo {
  disponibles(inscritos: number) {
    return Math.max(this.cupo - inscritos, 0);
  }
  verificarQueHayCupo(inscritos: number) {
    if (inscritos >= this.cupo)
      throw new ReglaIncumplida(
        `Ya no hay cupo en ${this.id}`, 'conflicto');
  }
  ocupacion(inscritos: number) { /* … */ }
}

La oferta, los reportes y las inscripciones le preguntan al paralelo. Math.max: «disponibles» nunca es negativo, como dice el glosario.

Una regla dentro de un objeto no se puede olvidar ni copiar mal.iSAQB · SEI12 / 18

Agregado

InscripcionDeGestion: se cambia como una unidad, solo a través de su raíz
Táctico

Un agregado es un grupo de objetos que se cambia como una unidad. La raíz es la única puerta de entrada y protege todas sus reglas.

Lo que protege, en orden

  • Materia repetida.
  • Máximo de créditos.
  • Cupo del paralelo.
  • Choque de horario.
  • Prerrequisitos.
crear()Valida todo y nace en PENDIENTE_PAGO.
→
registrarPago()Pasa a pagada.
→
retirar()Nunca la última materia.

Lo que queda en el servicio

El periodo, «ya está inscrito» y «el paralelo existe» necesitan datos (archivos, reloj): son de la aplicación. El dueño de la inscripción (403) es autorización. El servicio orquesta: busca, llama al agregado, cobra y guarda.

Por qué desde() copia los datos

Si guardara la misma lista que le pasan, alguien podría cambiarla desde afuera sin pasar por retirar(). Una prueba lo verifica.

Si hay que cambiarlo, se pasa por la raíz; si no, la regla no existe.iSAQB · SEI13 / 18

El dominio no sabe de HTTP

El dominio dice «esta regla no se cumple»; un filtro lo traduce a la respuesta
antes · el reglamento sabe de Nest 
if (creditos > MAX_CREDITOS) {
  throw new BadRequestException(
    'Supera el máximo de créditos');
}
después · el dominio lanza su propio error 
if (creditos > MAX_CREDITOS) {
  throw new ReglaIncumplida(
    'Supera el máximo de créditos', 'invalida');
}
tipo de reglaHTTP
invalida · la petición no cumple el reglamento400
conflicto · el estado no lo permite (sin cupo)409

Un filtro de excepciones, en un solo lugar

Registrado con APP_FILTER, se aplica a toda la app. Responde con la misma forma que usa Nest: el contrato no cambia.

La ganancia

src/inscripciones/dominio/ no importa Nest ni Node: se prueba en milisegundos, y una regla vigila que siga así.

El reglamento no debería cambiar si mañana Cupo deja de ser una API HTTP.iSAQB · SEI14 / 18
